## 1. 项目简介

**TSAD Dashboard**
是一个轻量级的时间序列异常检测与可视化平台。它面向服务器运行指标、系统监控数据以及其他按时间记录的数值型数据，提供数据导入、指标选择、异常检测、图表展示和结果导出功能。

项目将异常检测算法与 Streamlit Web
页面结合起来。使用者不需要先编写一套完整的数据分析程序，而是可以在网页中上传
CSV 文件、选择时间列和指标列、配置算法参数，然后查看检测结果。

-   **项目名称：** TSAD Dashboard
-   **项目类型：** Python 数据分析 / 时间序列异常检测 / Web 可视化
-   **主要用途：**
    课程项目演示、监控数据探索、异常检测算法对比和结果分析
-   **界面框架：** Streamlit
-   **算法基础：** PyOD
    中的通用异常检测算法，以及项目实现的时间序列检测方法
-   **GitHub：** <https://github.com/liaooss/TSAD-Dashboard>
-   **在线演示：** <https://tsad-dashboard.streamlit.app/>

> 注意：异常检测结果是算法基于数据和参数给出的"可疑点"，不等同于已经确认的故障。实际运维场景还需要结合业务规则、日志、告警和人工判断。

## 2. 为什么需要时间序列异常检测

在服务器和软件系统运行时，通常会持续记录各种指标，例如：

-   CPU 使用率；
-   内存使用率；
-   磁盘读写量；
-   网络流量；
-   请求延迟；
-   每秒请求数；
-   错误请求数量。

这些数据通常带有时间戳，例如每隔 10 秒记录一次 CPU
使用率。把按时间先后排列的一组观测值称为**时间序列**。

正常情况下，指标会在一定范围内波动。但如果发生资源耗尽、服务异常、流量突增或采集系统问题，数据可能突然出现不寻常的变化。异常检测的目标，就是从大量观测中筛选出值得进一步检查的点或时间段。

### 一个简单例子

  时间         CPU 使用率
  ---------- ------------
  10:00:00            21%
  10:00:10            23%
  10:00:20            22%
  10:00:30            24%
  10:00:40            96%
  10:00:50            25%

如果 CPU 使用率平时在 20% 左右波动，而某个时刻突然升至
96%，这一点就可能值得关注。但它是否真的是故障，还需要进一步检查：它可能是正常的批处理任务，也可能是程序失控或业务流量突增。

这类从监控数据中发现可疑行为的工作，是
AIOps（智能运维）中的一个常见方向。

## 3. 核心概念入门

### 3.1 时间序列（Time Series）

时间序列是按照时间顺序排列的数据。它通常包含两类信息：

1.  **时间列：** 记录每条数据对应的时间，例如 `timestamp`。
2.  **数值列：** 记录某个指标的值，例如 `cpu_usage` 或 `memory_usage`。

如果数据没有明确时间列，也可以按样本顺序分析，但图表横轴就只能表示样本序号，而不是真实时间。

### 3.2 指标（Metric）

指标是被观察的数值变量。例如 CPU 使用率和内存使用率是两个不同指标。一个
CSV 文件可以包含多个指标，每个指标的异常表现也可能不同。

### 3.3 异常点（Anomaly）

异常点是相对于数据整体模式显得不寻常的观测。常见情况包括：

-   **点异常：** 某个点明显高于或低于周围数据；
-   **持续异常：** 一段时间内数值持续偏高或偏低；
-   **上下文异常：**
    数值本身未必极端，但在当前时间、负载或业务背景下不合理；
-   **趋势或漂移异常：** 指标的基线或变化趋势逐渐偏离正常模式。

项目可以帮助定位可疑点和连续异常区间，但具体的业务含义仍需要分析者判断。

### 3.4 异常分数（Anomaly Score）

许多算法不仅给出"正常 /
异常"的判断，还会为每条记录计算一个异常分数。分数越高，通常表示该点越可疑。

不同算法原生分数的范围和含义可能不同。因此，页面中如果显示归一化到 0--1
的异常分数，应把它理解为**便于在同一界面查看的相对分数**，而不要直接当作"异常发生概率"。例如，0.9
不代表有 90% 的概率发生故障。

### 3.5 阈值（Threshold）

阈值用于把连续的异常分数转换成异常 / 正常标签：

-   分数达到或超过阈值：标记为异常；
-   分数低于阈值：标记为正常。

降低阈值通常会标记更多异常点，也可能增加误报；提高阈值通常会减少异常点，但可能漏掉部分真实异常。合适的阈值取决于数据和业务目标。

### 3.6 预期异常比例（Contamination）

部分通用异常检测算法需要指定一个预期异常比例，例如
0.05（5%）。它表示算法在确定异常标签时使用的比例假设或参考参数，**不表示数据中已经确认有
5% 的真实故障**。

如果实际数据非常干净，设置过高可能产生较多误报；如果异常很多，设置过低可能漏检。建议将它作为实验参数进行比较，而不是把默认值当成客观真值。

### 3.7 标签与评价指标

如果数据集本身提供了人工确认的真实标签（例如某些行明确标记为异常），就可以把算法预测与真实标签对比。常见评价指标有：

-   **Precision（精确率）：**
    被算法判为异常的点中，有多少确实是异常。精确率低意味着误报较多。
-   **Recall（召回率）：**
    所有真实异常中，有多少被算法找出来。召回率低意味着漏检较多。
-   **F1：** 精确率与召回率的综合指标。

如果 CSV
没有真实标签，就不能仅凭算法自己输出的结果计算可靠的精确率、召回率或
F1。没有标签时，可以检查图表、抽样核验异常点，并与运维记录交叉验证。

## 4. 项目能做什么

项目页面围绕一次完整的分析流程组织功能。

### 4.1 数据导入与指标选择

-   上传 CSV 数据文件；
-   根据数据内容选择时间列；
-   选择需要分析的数值型指标；
-   查看数据概览，帮助确认数据是否正确读入。

### 4.2 数据预处理

根据当前版本页面提供的选项，可对时间和数值数据进行整理，例如时间解析、缺失值处理、重复时间戳检查、重采样、归一化等。预处理设置会影响后续检测结果，因此应记录所使用的配置。

-   **缺失值处理：** 对空值进行处理，避免算法因无法计算而失败。
-   **重复时间戳：**
    同一时间出现多条记录时，应确认这是合理的多条采样，还是需要合并的数据。
-   **重采样：**
    将数据转换到指定的时间间隔，适用于采样频率不一致的情况。
-   **归一化：**
    把不同量纲或范围的数值转换到更可比较的尺度。不同算法对尺度的敏感程度不同。
-   **无效时间或数值：**
    应在检测前检查并处理，否则可能影响图表或算法运行。

请以实际运行版本中可见的选项为准；不同版本的功能可能有所调整。

### 4.3 多算法异常检测

项目提供多个算法供用户选择，并可查看异常分数和预测标签。通用算法与专门的时间序列方法各有适用场景，具体说明见"检测算法介绍"。

### 4.4 交互式图表

-   查看指标随时间变化的曲线；
-   在图表中定位异常点；
-   查看异常分数及阈值；
-   缩放图表、悬停查看数据细节；
-   查看异常点数量等统计信息；
-   观察连续异常点形成的时间区间。

### 4.5 结果导出

页面支持将分析结果下载为 CSV
文件；当前版本还提供不同类型的结果导出选项时，可分别保存完整结果、异常记录或算法比较结果。若提供
HTML 报告导出，也可以保存交互式图表供离线查看。

## 5. 系统工作流程

可以把整个系统理解为下面的处理链路：

``` text
CSV 文件
   │
   ▼
读取数据并检查列
   │
   ▼
选择时间列与待检测指标
   │
   ▼
数据预处理
（时间解析、缺失值、缩放等）
   │
   ▼
选择算法并设置参数
   │
   ▼
计算异常分数
   │
   ▼
根据阈值生成异常标签
   │
   ▼
展示指标曲线、异常点和统计结果
   │
   ▼
导出 CSV / 报告并进一步分析
```

每一步都可能影响结果。例如，时间列解析错误会影响横轴；缺失值处理方式会影响数据；预期异常比例或阈值会影响最终被标记的点。因此，分析时不应只记录算法名称，还应记录数据来源、指标、预处理方式和参数。

## 6. 检测算法介绍

本节介绍常见思路，而不是数学推导。算法的实际表现会受数据规模、噪声、趋势、周期性和参数影响。

### 6.1 Isolation Forest（孤立森林）

**直观想法：**
如果一个点和大多数数据差异很大，通常更容易通过随机切分把它单独分离出来。孤立森林利用这种"被孤立的难易程度"来判断异常。

**优点** - 通常适合中等规模的多维数值数据； -
不需要事先知道每个异常的具体形状； - 对复杂数据的适应能力较好。

**局限** - 原生方法是通用异常检测算法，并不自动理解时间顺序； -
仅输入单个时刻的数值时，可能无法识别周期、趋势或前后关系； -
本项目会利用窗口或相邻样本特征等方式帮助其处理时间序列，但效果仍取决于特征构造和参数。

**适合尝试：** 希望先建立一个通用基线，找出明显偏离整体分布的点。

### 6.2 LOF（Local Outlier Factor，局部离群因子）

**直观想法：**
比较一个点与其邻近点的局部密度。如果某个点所在区域的密度明显低于周围邻居，它就可能是局部异常。

**优点** - 能发现相对于局部邻域异常的点； -
当不同区域的数据密度不同时，有时比单纯的全局方法更有优势。

**局限** - 对邻居数量等参数较敏感； -
数据量较大时可能消耗较多计算资源； - 通用 LOF
本身不理解时间顺序，需要合适的特征或窗口表达时间关系。

**适合尝试：** 某个点不一定是全局最大或最小，但与附近数据明显不一致。

### 6.3 KNN（K-Nearest Neighbors，K 近邻异常检测）

**直观想法：**
找到每个样本最近的若干个邻居。如果一个样本离邻居都很远，它可能是异常点。

**优点** - 思路直观，容易理解； - 可作为比较不同异常检测方法的基线。

**局限** - 对特征尺度敏感；单位差异很大的指标可能主导距离计算； -
邻居数量会影响结果； - 大数据集上计算距离可能较慢； -
同样需要注意时间顺序是否被特征表达出来。

**适合尝试：** 数据规模不太大，希望使用容易解释的距离类方法。

### 6.4 Spectral Residual（频谱残差，SR）

**直观想法：**
时间序列中可能包含重复模式或较平滑的背景趋势。频谱残差方法尝试从频域表示中提取较难由背景模式解释的变化，再形成异常分数。

**优点** - 面向时间序列中的局部异常检测； -
可作为与通用离群检测算法不同思路的对照。

**局限** - 对窗口长度、序列形态和边界处理等因素可能敏感； -
不保证适用于所有周期、趋势或采样频率； -
检测出的可疑点仍需要结合原始曲线检查。

### 6.5 Matrix Profile（矩阵剖面）

**直观想法：**
将序列切成许多长度相同的小片段（子序列），比较每个片段与其他片段的相似程度。如果某段与其他片段都不相似，它可能是一个异常片段。

**优点** - 能从子序列角度发现不常见的局部形态； -
对"形状异常"或不常出现的模式有分析价值。

**局限** - 子序列长度会显著影响结果； -
序列很长时，计算可能较慢或占用较多内存； -
它关注的是片段形状的独特程度，不一定等同于业务上的故障。

### 6.6 如何选择算法

  你的目标                 可以先尝试          需要注意
  ------------------------ ------------------- --------------------------
  快速建立通用基线         Isolation Forest    时间关系需要通过特征表达
  找局部密度不一致的点     LOF                 邻居参数和特征尺度
  用距离直观地找离群点     KNN                 归一化与计算成本
  分析局部时间序列异常     Spectral Residual   序列形态和参数
  寻找不常见的子序列形状   Matrix Profile      子序列长度与运行时间

不要仅凭"异常点数量更多"就判断某个算法更好。一个算法可能找到更多真正的异常，也可能只是产生更多误报。最好的判断依据是已知标签、人工核验和实际业务背景。


-   **原 PyOD 文件：** 仓库中还包含 PyOD 相关代码或项目文件。Dashboard
    是在其基础上增加的 Web 应用，不应随意删除原项目文件。

## 9. 本地安装与运行

### 9.1 获取代码

如果已经克隆项目，可直接跳到下一步。否则打开终端，执行：

``` bash
git clone https://github.com/liaooss/TSAD-Dashboard.git
cd TSAD-Dashboard
```

### 9.2 创建独立环境（推荐）

如果使用 Conda：

``` bash
conda create -n tsad-dashboard python=3.11 -y
conda activate tsad-dashboard
```

独立环境可以避免项目依赖与电脑中其他 Python 项目互相干扰。

### 9.3 安装依赖

在项目根目录执行：

``` bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

如果仓库当前版本要求单独安装 Dashboard 依赖，并且
`requirements-dashboard.txt` 存在，也可以按仓库实际配置执行：

``` bash
python -m pip install -r requirements-dashboard.txt
```

如果安装过程中出现报错，请先保留完整错误信息，不要立刻删除原有环境或升级所有包。优先确认
Python 版本、当前激活的环境和依赖文件内容。

### 9.4 启动应用

在项目根目录执行：

``` bash
python -m streamlit run app.py
```

终端会显示本地地址，通常类似：

``` text
http://localhost:8501
```

用浏览器打开该地址即可使用。停止服务时，回到运行 Streamlit 的终端按
`Ctrl + C`。

### 9.5 Windows 当前环境的启动方式

如果使用本项目现有的 Conda 环境，可以执行：

``` bat
conda activate tsad-dashboard
cd /d E:\Projects\TSAD-Dashboard
python -m streamlit run app.py
```

其中 `E:\Projects\TSAD-Dashboard`
是本机项目目录示例。如果你把项目放在其他位置，应替换为自己的路径。

### 10.1 推荐的 CSV 格式

最简单的数据可以长这样：

``` csv
timestamp,cpu_usage,memory_usage
2026-10-01 10:00:00,21.5,61.2
2026-10-01 10:00:10,22.1,61.5
2026-10-01 10:00:20,21.8,61.4
2026-10-01 10:00:30,95.7,62.0
2026-10-01 10:00:40,23.0,61.7
```

说明：

-   `timestamp` 是时间列；
-   `cpu_usage` 和 `memory_usage` 是数值指标；
-   每一行是一条观测记录；
-   每行的时间和数值应对应正确。

### 10.2 数据准备建议

1.  **确认 CSV 编码。** 如果中文列名显示乱码，尝试将文件另存为 UTF-8
    编码。
2.  **确认时间格式。** 时间列最好采用一致且明确的格式，例如
    `YYYY-MM-DD HH:MM:SS`。
3.  **确认指标为数值。** 避免数值列混入"未知""--"等文字。
4.  **按时间排序。** 时间序列分析通常需要按时间先后排列。
5.  **检查缺失值。** 不要在不了解业务含义的情况下直接把所有空值当成 0。
6.  **留意重复时间。**
    重复时间戳可能是重复采集，也可能是同一时刻多条合法记录。
7.  **先使用小样本。**
    首次尝试可先取一段代表性数据，确认配置和图表正常，再处理更长的文件。

### 10.3 多指标数据

一个文件可以包含多个数值列，例如
CPU、内存和网络流量。不同指标的单位和正常范围可能不同，因此：

-   选择指标时，确认它确实是你想分析的目标；
-   不要把时间戳、服务器名称、日志文本等非数值列当作数值指标；
-   如果不同指标量纲差异很大，应考虑是否需要归一化；
-   各指标同时异常不一定意味着它们有同一个原因。

### 10.4 有标签的数据

如果你有人工确认的异常标签，可以额外保留一列，例如：

``` csv
timestamp,cpu_usage,label
2026-10-01 10:00:00,21.5,0
2026-10-01 10:00:10,22.1,0
2026-10-01 10:00:20,95.7,1
```

这里只是示例。`0` 和 `1`
的含义必须与应用实际支持的标签格式一致。请检查页面或代码中标签列的识别方式，不要假定任意名为
`label` 的列都会自动用于评价。

## 11. 页面使用教程

### 第一步：打开网页

本地启动成功后，在浏览器打开 Streamlit
地址。页面侧边栏包含项目名称、功能导航和检测配置，主页面用于数据导入、结果展示和图表分析。

### 第二步：导入 CSV

在数据导入区域上传 CSV 文件。导入后先查看数据预览和概览，确认：

-   行数与列数是否合理；
-   时间列有没有被正确读取；
-   指标列是否为数值；
-   是否存在大量空值或格式异常。

如果预览结果不符合预期，应先修正文件格式，而不是直接开始检测。

### 第三步：选择时间列和指标列

-   选择包含时间信息的列；
-   选择需要检测的数值指标；
-   如果没有时间列，确认应用是否支持按样本序号分析。

建议第一次只选择一个指标。这样更容易理解曲线与异常分数之间的关系。熟悉后再分析多个指标。

### 第四步：配置预处理和算法

根据数据情况设置缺失值处理、缩放或其他可用预处理选项，然后选择检测算法。

首次实验建议：

1.  使用默认配置运行一次；
2.  记录算法、指标和参数；
3.  观察异常点是否集中在明显突变的位置；
4.  再只修改一个参数进行对比。

一次同时修改很多参数，会让你很难判断结果变化究竟由什么引起。

### 第五步：运行检测

点击页面中的检测或分析按钮（具体名称以当前页面为准）。应用会根据所选数据和参数计算异常分数、生成异常标签，并显示统计和可视化结果。

对于较长序列或计算成本较高的算法，处理时间可能更长。尤其是需要比较大量子序列的算法，建议先用较短数据测试。

### 第六步：观察时间序列图

重点观察：

-   异常点是否对应尖峰、骤降或趋势变化；
-   异常点是孤立出现还是连续成段；
-   是否有明显周期性，异常点是否只是正常周期波动；
-   数据缺失或采样不均匀是否影响判断；
-   预处理前后的数据是否改变了原始量纲。

不要只看异常点颜色或数量，最好同时查看原始曲线和异常分数。

### 第七步：检查统计和异常区间

统计卡片或汇总图可以帮助你快速了解异常点数量及其在各指标上的分布。若页面显示连续异常区间，可以进一步查看每个区间的起止时间和持续样本数。

注意：同一时间点可能在多个指标上都被标记，因此"各指标异常点数量之和"可能大于"唯一异常时间点数量"。应先确认统计口径，再进行比较。

### 第八步：导出结果

在结果导出区域下载 CSV
或页面提供的其他格式。建议给文件起包含日期、指标和算法的名字，例如：

``` text
cpu_usage_isolation_forest_2026-10-21.csv
```

这样更容易追溯不同实验的结果。

## 12. 如何理解检测结果

### 12.1 异常标签不等于故障结论

算法只根据输入数据和模型假设找出可疑点。异常可能来自：

-   真实系统故障；
-   计划内的批处理或流量高峰；
-   采集延迟、丢点或重复上报；
-   部署、扩容或配置变更；
-   指标单位或数据格式错误。

因此，建议把结果用于缩小排查范围，而不是直接作为自动故障结论。

### 12.2 为什么算法找出的异常数量不同

不同算法对"异常"的定义不同。Isolation Forest
关注样本被孤立的难易程度；LOF 关注局部密度；KNN
关注与邻居的距离；Spectral Residual 和 Matrix Profile
则从时间序列局部变化或子序列形态出发。因此，同一份数据出现不同结果是正常现象。

### 12.3 为什么调高阈值后异常变少

阈值越高，通常越难达到异常判定条件，所以被标记的点会减少。阈值越低则相反。建议同时查看异常分数分布和曲线，不要为了让结果"看起来合理"而随意调到某个数量。

### 12.4 为什么真实异常没有被检出

可能原因包括：

-   异常幅度很小；
-   异常持续时间较长，但算法只擅长找尖峰；
-   周期、趋势或季节性没有被充分建模；
-   预处理平滑了异常；
-   阈值过高或预期异常比例设置不合适；
-   选择的指标不包含足够信息；
-   异常发生在训练或检测窗口的边界附近。

可以尝试更换算法、调整参数、检查预处理方式，并结合人工标签验证。

### 12.5 为什么正常点被误判为异常

常见原因包括：

-   正常业务峰值本身很少见；
-   数据包含突发但合法的任务；
-   数据分布随时间发生变化；
-   数据尺度或缺失值处理不合适；
-   参数设置使算法标记过多样本。

应结合业务上下文判断，不要把"少见"直接等同于"错误"。

### 12.6 分数能否跨算法直接比较

不一定。即使界面把分数归一化到相似范围，各算法的原始评分机制仍不同。跨算法比较时，应优先比较预测结果与真实标签的一致性、异常点的位置、误报漏报情况和业务可解释性，而不是简单地认为分数更高的算法更好。

## 13. 结果导出

导出文件的具体列名由当前版本实现决定。通常可以关注以下信息：

-   时间戳或样本序号；
-   原始指标值；
-   异常分数；
-   是否被判为异常；
-   算法或配置相关字段（若有）。

建议保留原始数据副本，不要只保存检测后的文件。对每次实验记录以下内容：

-   数据文件来源与时间范围；
-   检测指标；
-   使用的算法；
-   预处理方式；
-   阈值或预期异常比例；
-   检测日期；
-   人工核验结论。

这样能让课程报告中的实验更可复现。

## 14. 技术栈说明

### Python

主要开发语言。负责数据处理、调用算法、计算分数和控制页面逻辑。

### Streamlit

把 Python
脚本转化为网页交互界面。它让项目可以通过浏览器完成上传文件、调整参数、显示表格和图表，不需要单独编写前端框架和后端
API。

### Pandas 与 NumPy

Pandas 主要负责 CSV 表格、列选择、缺失值处理和数据整理；NumPy
主要负责数值数组、向量化计算和数值转换。

### Plotly

负责绘制交互式时间序列图、异常分数图和统计图。用户可以悬停查看细节、缩放时间范围，并更方便地定位可疑点。

### PyOD 与相关算法库

PyOD
提供多种通用异常检测算法。本项目将其中的算法整合进页面，并结合时间序列数据的特点处理输入。并非所有方法都原生具备时间序列建模能力，因此要区分通用离群检测与专门的时序方法。

## 15. 项目适用场景与局限

### 适用场景

-   学习时间序列异常检测的基本概念；
-   对 CSV 格式的监控指标进行探索；
-   比较不同异常检测方法的输出；
-   在课程展示中演示从数据导入到结果可视化的完整流程；
-   对候选异常点进行初步筛选。

### 当前局限

-   **不是完整的生产级 AIOps 平台。**
    当前项目主要针对文件导入和交互式分析，不应假定已经具备生产环境所需的认证、权限、审计、告警路由或高可用能力。
-   **不等同于实时监控系统。** 除非另行实现数据流接入，否则上传 CSV
    分析不等于持续实时检测。
-   **通用算法不一定理解时间依赖。**
    需要考虑窗口特征、周期、趋势和采样间隔。
-   **结果需要验证。** 没有可靠标签时，很难客观证明某个算法一定更好。
-   **数据质量很重要。**
    时间错乱、缺失值、异常单位和重复记录都会影响结果。
-   **计算成本有差异。**
    对很长的序列，应关注内存、运行时间以及子序列算法的复杂度。
-   **在线演示的可用性受部署环境影响。**
    免费服务可能休眠、重启或有资源限制；本地运行更适合较大数据实验。

## 16. 常见问题

### Q1：运行 `streamlit run app.py` 提示找不到命令怎么办？

先确认已激活项目环境，然后使用：

``` bash
python -m streamlit run app.py
```

如果提示没有安装 Streamlit，执行：

``` bash
python -m pip install streamlit
```

更推荐按项目依赖文件安装全部依赖。

### Q2：导入 CSV 后没有可选指标怎么办？

检查目标列是否为数值类型，是否混有文字、百分号或其他非数字字符。必要时在
Excel 或 Pandas 中清理数据后再上传。

### Q3：时间轴显示不正确怎么办？

检查时间列是否选对、格式是否统一、是否包含无法解析的值，以及数据是否按时间排序。如果没有时间列，图表可能只能按样本序号显示。

### Q4：为什么检测速度很慢？

数据行数较多、指标较多或算法计算复杂，都可能增加运行时间。可以先抽取一段较短数据，减少指标数量，或尝试更轻量的算法。

### Q5：异常点太多怎么办？

检查预期异常比例和阈值设置，确认是否存在数据质量问题，再尝试不同算法。不要仅为减少异常数量而忽略潜在的真实异常。

### Q6：异常点太少怎么办？

检查阈值是否过高、数据是否经过过度平滑、异常是否幅度较小，并尝试其他算法或特征表达方式。异常少并不必然代表算法更好。

### Q7：算法之间结果不一致，是不是程序有问题？

不一定。算法基于不同假设，输出不一致很常见。应先确认输入数据和参数一致，再查看每个算法的异常位置与评分机制。

### Q8：如何把代码更新到 GitHub？

在项目根目录执行：

``` bash
git status
git add app.py README.md .streamlit/config.toml
git commit -m "docs: update project documentation"
git pull --rebase origin master
git push origin master
```

如果 `git pull --rebase` 出现冲突，需要按 Git
提示解决冲突后再继续。不要在不清楚后果时使用
`git push --force`，因为它可能覆盖远程提交。

### Q9：在线部署后页面没有更新怎么办？

确认代码已经成功推送到部署所连接的 GitHub
仓库和分支，再查看部署平台的构建日志。部署服务可能需要一些时间重新构建。若构建失败，应先检查日志中的依赖安装错误或
Python 版本问题。

## 17. 课程展示建议

如果你要向老师或同学演示，可以按以下顺序介绍：

1.  **问题背景：** 服务器指标不断产生数据，人工逐条查看成本高。
2.  **项目目标：** 将 CSV 数据、算法、可视化和导出流程整合到一个网页。
3.  **数据展示：** 上传一份包含时间戳和监控指标的示例 CSV。
4.  **算法演示：** 使用相同数据切换 Isolation Forest、LOF、KNN
    或时序方法。
5.  **结果解释：**
    指出曲线上的候选异常点，结合异常分数和参数说明判定过程。
6.  **结果对比：**
    比较不同算法检测到的位置和数量，强调数量多不代表性能一定好。
7.  **结果导出：** 下载 CSV，说明如何将结果交给后续分析流程。
8.  **局限与展望：**
    说明当前主要面向离线文件分析，后续可探索实时数据接入、真实标签评估和告警功能。

演示时最好准备一份小型、可解释的数据集：大多数点较平稳，在少数位置加入明显尖峰或持续变化。这样便于观众理解算法输出。但在报告中应明确说明这是合成演示数据，不能把人工植入的异常当成真实生产故障。

## 18. 后续可改进方向

在现有项目基础上，可以考虑以下扩展方向：

-   **真实数据集评估：** 使用公开的服务器监控或时间序列异常数据集，计算
    Precision、Recall、F1 等指标。
-   **算法对比实验：**
    固定同一数据集和预处理方法，系统比较算法表现和运行时间。
-   **周期性与趋势处理：** 引入更适合季节性、趋势变化和概念漂移的方法。
-   **多变量异常检测：** 研究
    CPU、内存、网络等指标之间的相关关系，而不只逐列检测。
-   **实时数据接入：** 从 Prometheus
    等监控系统读取数据，逐步实现持续检测。
-   **告警与事件关联：**
    将异常区间与日志、发布记录或服务事件关联，减少无效告警。
-   **实验配置保存：** 保存每次算法、参数、指标和数据版本，便于复现。
-   **自动化测试：**
    为数据清洗、异常分数计算、导出和关键页面逻辑添加测试。
-   **部署与安全：**
    增加访问控制、数据保密、资源限制和更完善的部署配置。

这些属于可继续开发的方向，并不代表当前版本都已实现。

## 总结

TSAD Dashboard
的核心价值，是把时间序列异常检测的几个主要步骤串联起来：**导入数据 →
选择指标 → 配置算法 → 计算异常分数 → 可视化检查 → 导出结果**。

对初学者来说，建议先理解时间序列、异常分数、阈值和误报/漏报，再用一份简单
CSV
实际操作。学习过程中最重要的不是让算法"标出更多异常"，而是理解它为什么标记这些点、参数如何影响结果，以及如何通过标签或业务背景验证结论。

如果要将项目用于真实运维决策，应先通过真实数据和人工标签进行评估，再考虑实时接入、告警与生产部署。
